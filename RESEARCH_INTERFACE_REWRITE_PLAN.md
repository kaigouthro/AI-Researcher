# Research Interface + Research Vector Organization Rewrite Plan

## Goals
- Reorganize work so each **research topic lives in its own folder** with clear lifecycle state.
- Introduce a durable **metadata system** with tags, categories, project grouping, and cross-topic links.
- Add a **task pipeline model** so users can run predefined task sequences, reorder tasks, and queue future tasks.
- Provide a cleaner interface (CLI + web) that behaves like a project-oriented research workspace instead of ad-hoc demos.

## Product Principles
1. **Topic-first UX**: the top-level object is a research topic, not a script.
2. **Metadata before artifacts**: every item created should be indexable/searchable through metadata.
3. **Composable tasks**: tasks are reusable units with inputs/outputs and dependency rules.
4. **Reproducibility**: every run captures model, params, prompts, and generated artifacts.
5. **Safe evolution**: introduce the new system incrementally with migration tooling.

## 1) Target Information Architecture

### 1.1 Folder Layout (One Folder Per Research Topic)

```text
workspace/
  projects/
    <project_slug>/
      project.yaml
      topics/
        <topic_slug>/
          topic.yaml
          runs/
            <run_id>/
              run.yaml
              logs/
              artifacts/
              outputs/
          tasks/
            backlog.yaml
            templates/
          notes/
          references/
          vectors/
            index_manifest.json
            chunks.parquet
            embeddings/
```

### 1.2 Object Model
- **Project**: umbrella grouping for related topics (e.g., "Graph Recommendation 2026").
- **Topic**: one research question/hypothesis stream.
- **Run**: a concrete execution of a task plan on a topic.
- **Task**: a reusable operation in the research workflow.
- **Artifact**: file output generated by tasks.
- **Vector Set**: embeddings/chunks/index assets scoped to project/topic/run.

### 1.3 Metadata Files
- `project.yaml`: project-level metadata (owner, tags, default model policies).
- `topic.yaml`: topic intent, status, taxonomy tags, links to sibling topics.
- `run.yaml`: run config, model provenance, timing, success/failure summary.
- `backlog.yaml`: future/planned tasks with priority, dependencies, and state.
- `index_manifest.json`: vector index metadata (provider/model/chunking/checksum).

## 2) Metadata + Tagging System Design

### 2.1 Core Metadata Schema

Each `topic.yaml` should include:
- `id`, `slug`, `title`, `created_at`, `updated_at`
- `project_id`
- `category_tags` (domain taxonomy: gnn, optimization, medical, etc.)
- `method_tags` (transformer, contrastive learning, diffusion, etc.)
- `task_tags` (survey, benchmark, reproduction, ideation, writing)
- `status` (`draft`, `active`, `blocked`, `archived`)
- `priority` (`low`, `medium`, `high`, `critical`)
- `linked_topics` (topic IDs for relation graph)
- `linked_projects` (cross-project references)
- `source_references` (paper IDs, URLs, bib keys)
- `owner`, `contributors`

### 2.2 Taxonomy and Validation
- Add a controlled vocabulary file: `taxonomy.yaml`.
- Validate metadata with Pydantic models.
- Implement tag normalization (slug casing, de-duplication, alias map).
- Track `schema_version` for migration safety.

### 2.3 Search and Filtering
- Build filter APIs/UI for:
  - by project
  - by category/method/task tag
  - by status/priority
  - by last update and active run state
- Add "related topics" suggestions via shared tags + vector similarity.

## 3) Task System (Selectable + Ordered + Future Tasks)

### 3.1 Task Registry
Create a task registry where each task declares:
- `task_id`, `name`, `description`
- required inputs + output artifacts
- estimated runtime/cost class
- dependencies and optional predecessors
- retry and fallback strategy

### 3.2 Starter Task Catalog
1. `topic_intake` (problem statement, constraints)
2. `literature_discovery`
3. `paper_screening`
4. `concept_map_generation`
5. `hypothesis_generation`
6. `experiment_plan`
7. `prototype_implementation`
8. `evaluation_run`
9. `result_interpretation`
10. `report_draft`
11. `report_polish`
12. `next_task_recommendation`

### 3.3 Execution Modes
- **Template mode**: choose prebuilt pipelines ("Survey", "Reproduction", "Novel idea").
- **Composer mode**: user manually selects tasks and order.
- **Adaptive mode**: system proposes next tasks from outputs + metadata gaps.

### 3.4 Backlog and Future Tasks
- `backlog.yaml` stores:
  - `queued`, `ready`, `running`, `blocked`, `done`
  - dependency graph
  - rationale for why task was added
- Add a recommendation engine that appends future tasks (e.g., "insufficient baselines → add benchmark expansion task").

## 4) Research Vector Organization Strategy

### 4.1 Vector Scoping
Use explicit namespaces:
- `project/<project_id>` shared memory
- `topic/<topic_id>` topic-focused memory
- `run/<run_id>` ephemeral run context

### 4.2 Vector Metadata Fields
Every chunk embedding should carry:
- `chunk_id`, `source_path`, `source_type`
- `project_id`, `topic_id`, `run_id`
- `tag_set`
- `created_at`, `embedding_model`, `embedding_provider`
- `content_hash`, `token_count`, `language`

### 4.3 Index Lifecycle
- Build/update index after each run.
- Track `index_manifest.json` with checksums + model version.
- Add garbage collection for stale run-level vectors.
- Reindex only changed files (hash-based incremental indexing).

### 4.4 Retrieval Policy
- First retrieve from topic scope.
- Backoff to project scope for broader context.
- Optional global fallback with stricter relevance threshold.
- Add reranking with metadata-aware weighting (same tags/project boosted).

## 5) Interface Rewrite Plan (CLI + Web)

### 5.1 New Navigation Model
- **Projects page**: project list + health summary.
- **Topic workspace**: metadata panel, run history, task board, related topics.
- **Run detail view**: logs, artifacts, metrics, reproducibility info.
- **Backlog board**: queued/blocked/done tasks and dependency graph.

### 5.2 Core UX Features
- "Create Topic" wizard with taxonomy suggestions.
- "Task Pipeline Builder" drag/drop ordering + dependency checks.
- "Run from Template" quickstart flows.
- "Add Follow-up Task" from any artifact or failed run.
- In-context metadata editing with schema validation errors surfaced in UI.

### 5.3 Technical Approach
- Keep existing runtime components but wrap them behind a **topic service layer**.
- Add API boundaries:
  - Topic API (CRUD + metadata)
  - Task API (registry + queue + run)
  - Vector API (indexing + retrieval)
  - Run API (execution + provenance)
- Preserve backward compatibility by mapping legacy run outputs into topic folders.

## 7) Validation and Success Metrics

### Functional Acceptance
- User can create project → topic → choose task template → run pipeline.
- System stores all outputs in the topic folder and captures run metadata.
- User can queue future tasks and reorder pending tasks.
- Retrieval honors topic/project scoping and tag-based filtering.

### Operational Metrics
- Metadata validation pass rate > 99%.
- Incremental indexing reduces reindex time by at least 50%.
- Average time to launch a new topic run reduced by 40%.
- >80% of runs include auto-generated follow-up task recommendations.

### Quality Gates
- Schema tests for all metadata files.
- Integration tests for pipeline dependencies and reorder logic.
- Regression tests for backward compatibility on legacy demo outputs.
